# minigrep — TDD練習

TDDのペアプロ練習用プロジェクト。役割分担は次のとおり。

- **設計・テスト方針・レビュー**: Claude
- **実装**: 自分

## 作るもの

```
minigrep <query> <file_path>
```

ファイルの中から `query` を含む行を標準出力に出す。

## 設計（責務の分け方）

| 部品 | 責務 | テストのしやすさ |
|---|---|---|
| `search` | 文字列から一致する行を返す（純粋関数） | ◎ 単体テストの中心 |
| `Config` | コマンドライン引数を解釈し、足りなければエラーにする | ◎ I/Oなしでテストできる |
| `run` | ファイルを読む → 検索する → 出力する | △ I/Oを含むので薄く保つ |
| `main` | 上の部品をつなぎ、エラー時は終了コードを返す | × テストしない（極力薄く） |

方針: **ロジックはI/Oから切り離して、テストできる場所に寄せる。**

## テストTODOリスト（上から順に1つずつ）

### フェーズ1: search
- [ ] 1行だけ一致する
- [ ] どの行にも一致しないときは空になる
- [ ] 複数行が一致する
- [ ] 一致するのは「行の一部」でもよい

### フェーズ2: Config
- [ ] 引数が正しければ query と file_path を取り出せる
- [ ] 引数が足りなければエラーになる

### フェーズ3: run / main
- [ ] 存在しないファイルを渡すとエラーになる
- [ ] 実際に動かして確認する（`cargo run`）

### フェーズ4: 拡張（余力があれば）
- [ ] 大文字小文字を区別しない検索
- [ ] 環境変数やオプションで、区別するかどうかを切り替える

> 途中で新しいケースに気づいたら、すぐには実装せずにこのリストへ足す。

## 進め方のルール

1. 🔴 **Red**: テストを1つだけ書き、`cargo test` で**失敗するのを見届ける**
2. 🟢 **Green**: テストが通る**最小限**のコードを書く（ベタ書きでもよい）
3. 🔵 **Refactor**: テストが緑のまま、コードを整える
4. 1サイクル終わったらレビューを受けて、次のテストを決める

**コツ**: Greenではあえて「ずるい」実装を選ぶ。次のテストでそれが通らなくなり、一般化が必要になる流れを体験する。
